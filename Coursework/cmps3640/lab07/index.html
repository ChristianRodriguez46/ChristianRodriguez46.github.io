CMPS 3640 · Lab 7

Parallel histogram with locks

Builds a histogram of 100,000 random digits twice: with a plain loop, and with an OpenMP parallel loop that guards each of the 10 bins with its own lock. The write-up lab7.md explains why the locked parallel version ran about 39 times slower than the sequential one.

View code on GitHubREADME

What I did

  • Wrote seq_histogram.cpp, which fills an array with 100,000 random values from 0 to 9, counts them into 10 bins, and times only the counting loop with omp_get_wtime.
  • Wrote par_histogram.cpp with #pragma omp parallel for and an array of 10 omp_lock_t locks, set and unset around each increment, and initialized and destroyed the locks around the loop.
  • Measured both and recorded in lab7.md 0.000374 seconds sequential against 0.014644 seconds with 20 threads, about 39 times slower.
  • Gave four reasons in the write-up: almost no work per iteration (one increment), contention for 10 locks among 20 threads, the cost of setting and unsetting a lock compared with an increment, and the overhead of starting and coordinating 20 threads.
  • Concluded that parallelism pays off only when the computation outweighs the synchronization, and that the parallel version would need a far larger array (hundreds of millions of elements) to come out ahead.

How to build and run

From the folder with the code:

g++ -fopenmp -o seq_hist seq_histogram.cpp && ./seq_hist
g++ -fopenmp -o par_hist par_histogram.cpp && ./par_hist

Requires: g++ with OpenMP (-fopenmp) and POSIX threads (-pthread), standard on Linux.
